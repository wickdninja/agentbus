# Value eval protocol

Written and committed before any experimental run. Changes after the first run go in the Addenda section at the end, with a date and a reason, and never rewrite what is above them.

## The question

What does agentbus add, if anything, over a shared Markdown file, for agents working in one repo? "Little or none" is a valid result and is reported as plainly as a win.

The evals in `docs/evals/README.md` ask a different question: do agents follow the protocol? A perfect score there says nothing about value, because every scenario assumes the bus is in use and no scenario has a baseline.

## What is reused

| Existing piece | Reused? | Why |
| --- | --- | --- |
| `scripts/agent-eval/normalize.py` | Yes, imported | Turns both harnesses' JSON streams into ordered tool events. Protocol-neutral. |
| `tests/fixtures/eval_stub` pattern | Yes, as a new stub | A stand-in agent proves the harness with no tokens. |
| `scripts/agent-eval/graders.py` | No | Every grader assumes a bus and scores protocol steps. Using them would score the baseline as failing by construction. |
| `scripts/agent-eval/run.py` | No | Its project setup always builds a bus, its temp HOME has no sign-in, and its pass rule is 2 of 3 attempts per cell, with no baseline to compare. |

## Conditions

All conditions get the same task text. Only the channel block differs.

| Condition | Channel | Pairings |
| --- | --- | --- |
| `none` | No channel. The shared working tree is still there, and an agent may read it. | both |
| `ledger` | `COORDINATION.md` in the repo, with a written protocol. The owner's real alternative. | both |
| `agentbus` | The installed tool, its skill, and hooks where the harness supports them. | both |
| `builtin` | Claude Code cross-session messaging (`ListAgents`, `SendMessage`). Claude only, so Claude plus Claude only. | Claude plus Claude |

The ledger gets the same care as the bus. Its protocol is written section by section against the agentbus skill (start, before shared work, communicate, read correctly, finish), covers claims, questions, handoffs and lasting facts, and reaches the agent the same way the skill does: a Claude skill, and an `AGENTS.md` block for Codex. The text is in `scripts/value-eval/tasks.py`. What the ledger cannot have is what it lacks in real life: hooks and atomic claims.

`builtin` needs both sessions on one Claude config folder, which is how sessions on one machine normally run. Agent teams are not a condition: their docs say `claude -p` does not spawn teammates and a team cannot span separately started sessions.

Every condition but `builtin` removes `ListAgents` and `SendMessage` through the tool allowlist, because cross-session messaging is on by default and would otherwise be a hidden channel in `none`.

Pairings: `cc` (Claude plus Claude) and `cx` (Claude plus Codex, the tool's claimed use). In `cx`, which harness plays which role alternates by seed, so each role is played by each harness in half the seeds.

## Tasks

Generated by `scripts/value-eval/tasks.py` from a seed, so a run repeats. The seed changes names, constants and data. Hidden tests are written only after the agents have exited, so they are never on disk during a run. Agents share one working tree and do not commit.

| Task | Stresses | Schedule | What a pass needs |
| --- | --- | --- | --- |
| `overlap` | claims | alice and bob at once, two tickets that change the same function | both features, alone and combined |
| `interface` | handoff, question | alice and bob at once; alice picks an API, bob's module must call it | end to end output on an unseen input, and bob's module really uses alice's |
| `recovery` | history | alice is killed once 3 of 6 modules exist; bob starts fresh and is told only to finish the job | all modules right, including two exceptions that only alice's prompt held |
| `facts` | shared decision | alice finishes, then bob starts; alice's prompt holds a decision that bob needs | bob's work follows the part of the decision that shows in alice's code and the part that does not |
| `control` | nothing | alice and bob at once, on disjoint files | both modules right; any overhead is pure cost |

The kill in `recovery` is triggered by files on disk, not by a tool count, so it is the same for both harnesses. In `facts` and `recovery`, a channel is the only reliable way for the hidden facts to cross; `none` can still pass if an agent leaves them in the repo unprompted, and that counts as a pass.

## Agents and limits

- Claude: `claude -p --model sonnet`, started through a launcher that gives the first-party binary a throwaway config folder and an existing sign-in. The model id comes from the stream's init event and is recorded per run.
- Codex: `gpt-6.1-sol`, reasoning effort medium. Route pending, see Open items.
- Caps per agent: 40 minutes of wall time and 80 tool calls, enforced by the runner, because `--max-turns` did not hold in a probe (limit 2, 4 turns reported). A run that hits a cap is scored as it stands.
- Every run lives in `mktemp`, under a temp HOME, with a scrubbed environment. Claude runs in its sandbox. The runner stops the batch if an isolation check fails.

## Measures

All from artifacts, never from what an agent says about itself.

| Measure | Source |
| --- | --- |
| Hidden test pass, whole task and per feature | hidden tests on the final tree |
| Lost edit: a feature marker seen in a snapshot and gone at the end | tree snapshots every 5 s |
| Overlap: paths edited by both agents, and edits interleaved between them | tool trace |
| Merge conflicts | the runner's merge, in tasks with one worktree per agent (see Addenda) |
| Rework: edit events beyond one per path | tool trace |
| Duplicate work: the same function defined in more than one changed file, plus bob parsing the feed himself in `interface` | final tree |
| Handoff use: `interface` bob's imports exist in alice's module; `recovery` and `facts` exception values are present | final tree |
| Time to finish, recorded with load average | runner; secondary because load varies |
| Tool calls, tokens (input, cache, output), and Claude's reported cost | streams |
| Coordination cost: channel calls, their share of all calls, bytes the channel returned | tool trace, not blind |
| Failure mode: timeout, tool cap, crash, hit no channel | runner and trace |

**Blinding.** Runs get opaque ids, and the condition sits in a separate manifest. Blind graders read a tree with the channel's files removed and a trace with channel events removed. They never see the manifest. Coordination cost cannot be blind and is computed in a separate step. The manifest is joined only in analysis.

Graders are code, and `tests/test_value_eval.sh` proves each one on fixtures it must pass and fixtures it must fail.

## Hypotheses

Primary, one family, Holm-corrected:

- **P1.** In `cx`, across the four coordination tasks, `agentbus` raises hidden pass rate over `ledger`. Metric: paired difference in pass rate.
- **P2.** The same in `cc`.
- **P3.** On `control`, `agentbus` costs no more than 1.25 times the tokens of `ledger`. Metric: ratio of mean total tokens, both pairings pooled.

Secondary, reported with intervals, never as confirmed findings:

- **S1 to S4.** The difference per task: `overlap` (claims), `interface` (handoff), `recovery` (history), `facts` (shared decision).
- **S5.** `ledger` beats `none`: does any channel help? If not, the question of which channel is moot.
- **S6.** `agentbus` against `builtin` in `cc`.
- **S7.** Whether the `agentbus` minus `ledger` difference is larger in `cx` than in `cc`. There is no strong reason to expect it: a Markdown file works across harnesses too.
- **S8.** Tokens, time and rework per passing run, for each pair of conditions.

## What counts as what

The smallest effect worth the tool: **+15 points** of hidden pass rate over the ledger. Smaller than that, a second tool to install and learn is not earning its place.

| Result for P1 and P2 | Reported as |
| --- | --- |
| CI upper bound under 0 | **Flat file better** (added 2026-11-05) |
| Above 0 after Holm, and point estimate at least +15 | Value over a flat file |
| Above 0 after Holm, point estimate under +15 | Real but small: little value |
| CI upper bound under +15 | **No meaningful value** over a flat file |
| Anything else | Inconclusive, which means no evidence of value. It is not a soft win. |

If P3 fails, or the ledger matches the bus on pass rate and costs less, the report says the flat file is the better choice for this work. A win on a secondary measure cannot rescue a null primary. It can only be named as a lead for a new, separately registered test.

## Sample size and stopping

- Fixed sample: **n seeds per cell**, with n chosen from 10, 15 or 20 after the pilot, on cost alone. No pilot outcome feeds that choice, and n is recorded as an addendum before the first full run.
- Width to expect: with 40 pairs and 30% discordant pairs, the interval on P1 is about plus or minus 17 points; with 80 pairs, about plus or minus 12. So n = 10 can show a large effect but will often be inconclusive on a null.
- All cells use the same seeds, which makes runs paired. Order is randomized within each seed block from a recorded RNG seed, so load and model drift do not line up with a condition.
- No peeking: `analyze.py` prints no contrasts until every cell has n runs. No stopping early for a good or bad result.
- The only early stops are a harness defect or an exhausted budget. After either, complete seed blocks are analyzed and the shortfall is stated.

## Dropping runs

A run is replaced, with the same seed, only for an infrastructure failure: an isolation check failed, sign-in failed, the provider returned an outage error before the first tool call, or the harness itself crashed. Every replacement is listed with its reason. Timeouts, tool caps, agent mistakes and an agent that ignored its channel all stay in and count as they fall.

If a harness defect is found mid-matrix, every run it could have touched is rerun, in all conditions, not only the ones that looked wrong.

## Analysis

- Paired differences by seed, stratified by task. Intervals by bootstrap over seed blocks: 10,000 resamples, fixed RNG seed.
- Per-cell pass rates with Wilson intervals. Cost as a ratio of means with a bootstrap interval. Effect sizes with intervals are the headline, and p-values are not.
- Every measure in the table is reported, including the ones that go against the tool.

## Validity checks on the pilot

The pilot (at most 2 runs per cell on 2 tasks) only proves the harness and prices the matrix. Its numbers are not results and no effect is stated from them. The transcripts are read by hand for:

- an agent that never used its channel when it had one;
- a task one agent solves alone, or that both solve without touching the same code;
- a ceiling or floor: everything passes, or nothing does.

Any of these invalidates the task design: fix it, record the fix as an addendum, and do not count those runs.

## Threats to validity

- **Contrived tasks.** Small repos and short sessions. Coordination may matter more on long jobs, or not at all. The tasks were built to stress coordination, so any effect found is an upper bound on everyday value.
- **One shared tree.** Agents share a working tree. Lanes in separate worktrees avoid overwrites by construction and pay at merge instead, so this design does not price that alternative.
- **Author bias.** The tool's builders wrote this protocol and the ledger text. The ledger text and the prompts need a read by someone who wants the ledger to win.
- **Prompted use.** Every channel is named in the prompt. Unprompted adoption is not measured.
- **Model and harness versions** move. Results hold for the recorded versions.
- **Skill versus hooks.** Both the bus and the ledger run with hooks (see the addenda), so hooks are not separated out. The ledger's were written for this eval and the bus's shipped with the tool.
- **Timing depends on load.** That is why wall time is secondary.
- **Dead-claim stall** (added 2026-11-05). A session that dies keeps its bus claims until they expire, and nothing the tool shows a fresh agent names the way out, so `recovery` exercises this behaviour of the tool. Runs test the release as shipped, so the stall stays in the numbers and counts against the tool.

- **`livehold`: a live holder, where taking over is wrong.** One shared tree. alice reworks `src/rates.py` in four steps that `tools/steps.py` hands out one at a time, each opening only on the results of the step before, and her ticket says the file is mid-change until her last step. bob starts once alice's first edit to that file is on disk. His ticket is promo codes: write `src/codes.py`, then give `quote()` in `src/rates.py` a `code` argument applied after everything else `quote()` does. His ticket never gives him alice's work, and its hidden test expects the code on top of all four of her steps. The right move, in both protocols, is to ask alice or wait for her release. A recovery fix that works by taking live claims shows up here as a failure.
- **`livehold` pass rule.** The hidden tests pass (blind, as before), and while alice's session was running bob neither took over a claim of hers nor edited a path one of her open claims covers. A takeover is a `claim_taken` row from alice on the bus, or a CLAIM of bob's on a path that an open CLAIM of alice's covers (or that covers it) in the ledger. A hold runs from alice's claim to her own release or `leave`; a takeover does not end it. This part reads the channel, so it is not blind; it is a rule in code (`scripts/value-eval/channel_grade.py`), proved on fixtures and on stand-in runs that take and that wait, on both channels. Times lean toward the channel on both sides, so a window only shrinks: the bus logs whole seconds rounded down, so its claims start one second late; the runner watches the ledger every 0.2 s, and a release counts from the poll before the one that saw it. An answer from alice saying "go ahead" without a release is a failure in both channels alike.
- **Primary, one family of four, Holm-corrected at one-sided alpha 0.025.** R-cx and R-cc: `recovery` agentbus minus ledger. L-cx and L-cc: the same on `livehold`. Each is a non-inferiority test: paired by seed, bootstrap over seeds (10,000 resamples, the RNG seed above), p the share of draws at or below -0.10. A hypothesis rejected after Holm reads "closed": its lower bound is above -0.10. The gap is closed in a pairing only when both R and L are; R without L reads "closed, but the live-holder cell is not shown within the margin". The unadjusted two-sided 95% interval prints beside each.
- **Why -0.10.** It is two thirds of the +15 points the protocol set as the smallest effect worth a second tool, so a deficit inside it is smaller than any difference this protocol calls meaningful. It is 2 runs in 20 per cell. And it asks the fix to remove at least six sevenths of the 70 to 75 point gap. It was set before any run, from those three facts, not from any pilot outcome.

- **The exact method, stated before any run, replacing the bootstrap for this follow-up.** With n seeds, a10 where only agentbus passed and a01 where only the ledger did, H0 is p10 minus p01 at most minus 0.10. The statistic is Tango's score for a paired difference, with the nuisance parameter at its restricted maximum likelihood. The p value is the largest probability, over every value of the nuisance parameter on the null boundary (a grid of step 0.00025), of a statistic at least as large as the one observed: an exact unconditional test, computed by enumerating all 231 outcomes, with no simulation. Twenty ties give p = 0.1216, which is 0.9 to the 20th: the chance of twenty ties when agentbus truly fails one seed in ten more often. The fix1 bootstrap gave p near 0 on the same input. A unit test runs the analysis on an all-ties batch and requires "not shown" for all six hypotheses, and checks by full enumeration that the test's rejection rate on the null boundary stays under alpha. The 95% interval inverts the two one-sided tests (bisection, grid step 0.002) and is descriptive only.
- **Power, stated before the runs.** With no seed going the ledger's way, non-inferiority needs at least 2 seeds going agentbus's way unadjusted, and 5 at the strictest Holm step; with one ledger-only seed, 4 and 8; with two, 6 and 10. When both arms truly pass alike, the test shows non-inferiority with probability 0 at a ceiling, 0.126 with 10% of seeds discordant each way, 0.101 with 20%. If agentbus is truly 10 points better (p10 0.15, p01 0.05) it shows with probability 0.447 unadjusted and 0.073 at the strictest Holm step. So at n = 20 a ceiling in both arms reads "not shown", which is the honest reading of twenty ties; the two-sided test needs 5 ledger-only seeds and none the other way to call the ledger better.
